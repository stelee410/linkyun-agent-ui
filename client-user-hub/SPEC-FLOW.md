# Flow：创作者与用户会话工作台 — 产品规格说明

## 1. 背景与目标

在 **client-user-hub** 内新增独立界面 **Flow**，供**创作者**在登录后集中处理「自己与终端用户之间、经由 AI Agent 发生的对话会话」。

**目标：**

- 以「瀑布信息流」形式按时间浏览会话，快速识别 Agent、用户与近期内容。
- 在单会话内完成核验、介入回复、以及与会话相关的提示词调整。
- 通过数据规则将 Flow 呈现为**待创作者跟进的队列**：创作者处理过后，若用户侧无新的对话活动，则该会话不再出现在 Flow 列表中。

---

## 2. 角色与范围

| 角色 | 说明 |
|------|------|
| 创作者（Creator） | Flow 的唯一主要使用者；可查看列表、打开会话、执行下文操作。 |
| 用户（End User） | 在既有聊天/会话产品侧与 Agent 对话；其活动驱动会话「是否需要再次出现在 Flow」。 |
| AI Agent | 与用户对话的主体；列表项需展示其标识信息。 |

**范围：** 本规格描述 Flow 的界面与数据可见性规则；后端 API 形态、权限模型、与现有 Session/Message 表的映射在实现阶段对齐代码库后细化。

---

## 3. 信息架构

- 创作者登录后进入 **Flow**（与 hub 内其他入口并列的路由/导航项，具体命名与图标实现时确定）。
- **主视图：** 瀑布信息流（纵向滚动列表）。
- **详情：** 点击某条会话打开 **会话弹窗**（或抽屉）；确认后通过 **OK** 保存并关闭。

---

## 4. 主列表：瀑布信息流

### 4.1 列表语义

- 列表中**每一行对应一个 Session**（一次用户与某 Agent 下的对话会话实例）。
- **排序：** 按时间排序（建议默认**新活动在上**，即「最需要关注」优先；若与全局习惯不一致可在实现前确认）。

### 4.2 单行布局（三栏）

| 区域 | 内容 |
|------|------|
| 左 | **AI Agent**：名称、头像或业务约定下的 Agent 标识。 |
| 中 | **信息**：会话摘要或最近一条关键消息等（具体字段由产品与现有数据能力决定）。 |
| 右 | **User**：当前会话关联的终端用户标识（昵称、ID、头像等）。 |

### 4.3 列表数据来源与过滤

列表仅展示满足 **第 7 节可见性规则** 的 Session（见下文形式化条件）。

---

## 5. 会话弹窗：操作与保存

用户点击某条 Session 后打开弹窗，创作者可进行以下操作（可在同一弹窗内分区展示）：

| 能力 | 说明 |
|------|------|
| **标记 Verified** | 对会话或内容做「已核验」类标记；具体业务含义（合规、身份、质量等）由产品定义；是否影响列表见 **8.2**。 |
| **直接发信息** | 创作者向该会话发送消息（发送者身份、是否对用户可见、是否与 Agent 回复合并展示，实现前需定稿）。 |
| **修改 System Prompt** | 调整系统级提示词；**作用域须明确**（全局 / 创作者维度 / 仅本会话所在 Agent 配置等），见 **8.3**。 |
| **修改 Session Prompt** | 仅针对**当前 Session** 的附加指令或会话级提示。 |
| **OK** | 提交弹窗内有效变更并关闭；**创作者处理时间**的更新策略见 **6.2** 与 **8.1**。 |

未点 OK 的本地编辑可视为草稿；是否需「取消丢弃」等行为实现时补充。

---

## 6. 数据模型要求

### 6.1 Session 表（或等价实体）新增/明确字段

| 字段（建议名） | 类型 | 说明 |
|----------------|------|------|
| `creator_handled_at` | 可空时间戳 | 创作者**最后一次**在 Flow 中对该 Session 完成「处理」的时间（见 6.2）。 |
| `verified` 或等价 | 布尔或枚举 | 若产品需要持久化「Verified」状态，与此对应；字段名与枚举值实现时确定。 |
| `system_prompt` / `session_prompt` | 文本或可空 | 若与现有模型分离存储，需与会话、Agent 配置的关系在实现文档中写清。 |

现有 Session 上若已有 `updated_at`（或类似），须与 **7** 节规则中的「会话更新时间」语义对齐（见 **8.4**）。

### 6.2 `creator_handled_at` 的写入时机（待产品确认默认值）

建议在规格中二选一或组合，并在评审时定稿：

- **方案 A：** 每次点击 **OK** 且弹窗关闭时，更新 `creator_handled_at = now()`（无论是否修改了 prompt 或发消息）。
- **方案 B：** 仅在执行了特定动作（例如发送消息、勾选 Verified、保存 prompt）时更新。
- **方案 C：** 单独提供「标记已处理」与 OK 解耦（本版需求以 OK 保存为主，可暂不采用）。

**本规格推荐：** 默认采用 **方案 A**，保证「看过并确认关闭」即视为一次 handle，列表按 7 节规则隐藏，直至用户侧有新活动。

## 7. Flow 列表可见性规则（核心）

记：

- \(T_{\mathrm{session}}\)：会话的**用于比较的更新时间**（见 8.4，建议与「用户侧新活动」一致）。
- \(T_{\mathrm{handle}}\)：`creator_handled_at`（若为空，见 8.5）。

**不显示在 Flow 中** 当且仅当：

\[
T_{\mathrm{handle}} \text{ 非空} \;\land\; T_{\mathrm{session}} \le T_{\mathrm{handle}}
\]

等价叙述：**若会话的更新时间没有晚于创作者最后一次 handle 的时间**（即用户在你处理之后没有产生「计入 \(T_{\mathrm{session}}\)」的新活动），则该 Session **不出现在** Flow 列表。

**显示在 Flow 中** 当：

- `creator_handled_at` 为空（从未被创作者按规则记录 handle），或
- \(T_{\mathrm{session}} > T_{\mathrm{handle}}\)（用户侧在创作者上次 handle 之后又有新活动，需要再次跟进）。

实现时应用同一规则于列表查询与分页，避免前端仅过滤导致数据不一致。

---

## 8. 待澄清与依赖

### 8.1 OK 与 `creator_handled_at`

是否与「仅浏览未改任何字段」仍更新 `creator_handled_at` 一致，需产品最终确认（见 6.2）。

### 8.2 Verified 与列表

Verified 是否作为独立过滤条件（例如已 Verified 仍显示直到用户再发言），或仅作展示标签，需在迭代前明确。

### 8.3 System Prompt 作用域

修改后的 system prompt 影响范围必须写死为一种：全局、按 Agent、按创作者+Agent、或仅当前 Session 内生效等，否则易产生安全与一致性风险。

### 8.4 \(T_{\mathrm{session}}\) 的定义

若通用 `updated_at` 会在「创作者发消息、改 prompt」等操作时一并更新，则**不能**单独表示「用户后续是否有新对话」。建议：

- 优先使用 **`last_user_activity_at` / `last_user_message_at`** 等明确来源于用户侧的字段作为 \(T_{\mathrm{session}}\)；或
- 在文档与迁移中严格规定何种事件会推进「用于 Flow 的会话活动时间」。

### 8.5 `creator_handled_at` 为空

从未 handle 的会话应**默认出现在 Flow**（直至被处理一次），查询条件需显式处理 `NULL`。

---

## 9. 非功能性提示

- **权限：** 仅创作者（或具备同等权限的角色）可访问 Flow 与相关写接口。
- **审计：** Prompt 变更、Verified 变更、创作者代发消息建议保留操作者与时间，便于追溯。
- **实时性：** 列表是否在用户新消息后实时推送或轮询，由实现阶段决定。

---

## 10. 验收要点（草案）

1. 创作者登录后可进入 Flow，列表为三栏布局，按约定时间排序。
2. 点击 Session 打开弹窗，可执行 Verified、发消息、修改 system/session prompt，OK 后变更持久化。
3. Session 上可查询到 `creator_handled_at`（或等价字段），且在用户无新活动（按 8.4 定义）时，该 Session 不出现在 Flow 列表；用户有新活动后重新出现。
4. 边界：`creator_handled_at` 为空的会话出现在列表中（除非另有产品规则）。
